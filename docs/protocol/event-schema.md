# Event Schema — GLITCHGUARD Protocol v1

**Version:** 1.0.0  
**Status:** Stable  
**Location:** `docs/protocol/event-schema.md`

---

## Overview

All events transmitted between the Dabao firmware and the host backend use a versioned JSON schema. Schema validation is enforced on the host side. Any message that fails validation is rejected with a logged error — it is never silently accepted or misclassified.

---

## Schema Version 1

### Top-Level Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `schema_version` | string | Yes | Always `"1.0"` |
| `event_id` | string (UUID v4) | Yes | Globally unique event identifier |
| `timestamp_ns` | integer (u64) | Yes | Monotonic timestamp in nanoseconds (device clock) |
| `source` | enum | Yes | Origin of the event — see Source Enum below |
| `event_type` | enum | Yes | Classification of the event — see Event Type Enum |
| `severity` | enum | Yes | Severity classification |
| `experiment_id` | string | Yes | Experiment identifier (e.g. `"GG-001"`) or `"BASELINE"` |
| `device_session_id` | string | Yes | Non-sensitive session identifier (rotated on each boot) |
| `evidence` | object | Yes | Structured evidence payload (varies by event type) |
| `verification_status` | enum | Yes | Cryptographic or logical verification result |
| `response` | enum | Yes | Defensive action taken |

### Source Enum

| Value | Description |
|---|---|
| `hardware_sensor` | Directly read from a physical hardware sensor register |
| `software_simulator` | Generated by the Python fault simulation framework |
| `runtime_monitor` | Detected by the Xous monitoring service (software observation) |
| `reset_controller` | Derived from hardware reset source information |

> **Important:** `hardware_sensor` must only be used when the value comes from an actual hardware register read. Software simulations must always use `software_simulator`.

### Event Type Enum

| Value | Description |
|---|---|
| `NORMAL` | Normal operational heartbeat or status |
| `ANOMALY` | Unexpected or suspicious observation |
| `INTEGRITY_FAILURE` | Cryptographic or checksum verification failure |
| `HARDWARE_WARNING` | Hardware sensor indicates an alert condition |
| `RESET_EVENT` | System reset observed; source recorded |
| `HEARTBEAT_TIMEOUT` | Expected heartbeat not received within window |
| `RECOVERY` | Defensive recovery action completed |
| `SENSOR_UNAVAILABLE` | Hardware sensor queried but not accessible |

### Severity Enum

| Value | Description |
|---|---|
| `INFO` | Normal operation |
| `LOW` | Minor anomaly, no immediate action required |
| `MEDIUM` | Significant anomaly, monitoring intensified |
| `HIGH` | Critical anomaly, quarantine triggered |
| `CRITICAL` | Lockdown condition |

### Verification Status Enum

| Value | Description |
|---|---|
| `PASSED` | Integrity check passed |
| `FAILED` | Integrity check failed |
| `SKIPPED` | Verification not performed for this event type |
| `PENDING` | Verification in progress |
| `ERROR` | Verification could not be completed |

### Response Enum

| Value | Description |
|---|---|
| `NONE` | No action taken |
| `LOGGED` | Event recorded only |
| `ALERT` | Alert raised to monitoring service |
| `QUARANTINED` | Affected application quarantined |
| `VERIFYING` | Integrity verification initiated |
| `RECOVERED` | Application returned to normal after successful verification |
| `LOCKDOWN` | System entered lockdown after repeated failures |

## Evidence Payload Structure

The `evidence` object structure depends on the `event_type`.

### INTEGRITY_FAILURE

```json
{
  "expected_hash": "sha256:abc123...",
  "observed_hash": "sha256:def456...",
  "payload_id": "test-payload-001",
  "algorithm": "SHA-256",
  "hardware_accelerated": false
}
```

### HARDWARE_WARNING

```json
{
  "sensor_name": "glitch_detector",
  "register_address": "0x...",
  "register_value": "0x...",
  "threshold_exceeded": true,
  "documentation_ref": "baochip-1x datasheet §4.3.1"
}
```

### HEARTBEAT_TIMEOUT

```json
{
  "process_name": "test-application",
  "expected_interval_ms": 1000,
  "last_heartbeat_ns": 123456789,
  "elapsed_ns": 2100000000
}
```

### RESET_EVENT

```json
{
  "reset_reason": "WATCHDOG",
  "reset_source_register": "0x...",
  "previous_state": "NORMAL"
}
```

### NORMAL (Heartbeat)

```json
{
  "sequence_number": 42,
  "uptime_ns": 123456789,
  "active_experiments": ["GG-001"]
}
```

## Schema Validation

The host backend validates every incoming event against this schema using Pydantic v2 models defined in `host-tools/parsers/event_parser.py`.

Events that fail validation are:
1. Logged with full raw content to `logs/validation-failures.jsonl`.
2. Never inserted into the event database.
3. Counted against the connection's error rate.

---

## Schema Evolution

Schema version is carried in every event. Breaking changes require a new major version. The host backend will process `schema_version: "1.x"` events using the v1 parser unless the minor version adds required fields.
